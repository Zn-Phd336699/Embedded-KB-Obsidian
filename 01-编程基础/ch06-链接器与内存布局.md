## 6.1 F407 最小 ld 脚本解剖

```ld
MEMORY
{
  FLASH (rx)  : ORIGIN = 0x08000000, LENGTH = 1024K
  RAM   (rwx) : ORIGIN = 0x20000000, LENGTH = 128K   /* 还有 CCM 64K@0x10000000 */
}
ENTRY(Reset_Handler)
_estack = ORIGIN(RAM) + LENGTH(RAM);   /* 主栈顶=RAM末端，向下生长 */

SECTIONS
{
  .isr_vector : { KEEP(*(.isr_vector)) } > FLASH  /* KEEP 防 gc 删除 */

  .text : {
    *(.text*) *(.rodata*)
    _etext = .;
  } > FLASH

  /* .data：VMA 在 RAM，LMA 在 Flash —— 加载域/执行域分离的核心案例 */
  _sidata = LOADADDR(.data);
  .data : { _sdata = .; *(.data*) _edata = .; } > RAM AT> FLASH

  .bss (NOLOAD) : { _sbss = .; *(.bss*) *(COMMON); _ebss = .; } > RAM
}
```

**LMA/VMA 双域布局**：已初始化全局变量的初值存 Flash（LMA），上电由 Reset_Handler 逐字拷贝到 RAM（VMA）——这就是「初值为何存在 Flash」的答案。

## 6.2 启动文件三件事

```asm
Reset_Handler:
    ldr sp, =_estack          @ 1) 先有栈！
    bl SystemInit             @ 2) 时钟初始化(CMSIS 提供)
    ldr r0, =_sidata          @ 3) .data 搬运 + .bss 清零
    ldr r1, =_sdata
    ldr r2, =_edata
copy: cmp r1, r2
    itt lt
    ldrlo r3,[r0],#4
    strlo r3,[r1],#4
    blo copy
    ...                       @ .bss 清零同理写 0
    bl main
hang: b hang                  @ main 返回=异常兜底
```

## 6.3 自定义段的工程价值

```c
/* ① 关键数据放 CCM（CPU 专用 64K）——注意 DMA 不可达！ */
__attribute__((section(".ccmram"))) uint8_t fast_buf[4096];

/* ② 参数表放独立 Flash 页，升级固件不丢配置 */
__attribute__((section(".config"), used))
const device_cfg_t g_cfg = { .magic = 0xC0FFEE, .baud = 115200 };
/* ld 增加： .config 0x080FF000 : { KEEP(*(.config)) } > FLASH */

/* ③ 函数放 RAM 执行：擦写自身 Flash 时必须（同 bank 冲突） */
__attribute__((section(".ramfunc"), long_call))
void flash_program_page(void) { /*...*/ }
/* ld： .ramfunc : { *(.ramfunc*) } > RAM AT> FLASH，且启动代码要补搬运！ */
```

> [!danger] CCM RAM 的 DMA 陷阱
> F407 的 CCM(0x10000000) 只有 CPU 内核可达，**DMA1/DMA2 都摸不到**。把 ADC/DMA 缓冲放 CCM 的症状是「传输永远完不成或数据全零」。对策：DMA 缓冲统一放主 SRAM 并 32 字节对齐（Cache 一致性见 [[ch26-DMA与Cache一致性]]）。

## 6.4 栈三道防线

```c
/* 防线1：水位线（运行期）——启动时涂色，统计被冲掉的颜色=历史最深用量 */
#define STACK_CANARY ((uint8_t)0xCD)
void stack_paint(void) {
    extern uint8_t _ebss, _estack;
    for (uint8_t *p = &_ebss; p < &_estack; p++) *p = STACK_CANARY;
}
uint32_t stack_used(void) {
    extern uint8_t _ebss, _estack;
    uint8_t *p = &_ebss;
    while (p < &_estack && *p == STACK_CANARY) p++;
    return (uint32_t)(&_estack - p);
}
/* 防线2：MPU 把栈底一页设 no-access → 溢出立即触发 MemManage 而非静默踩堆 */
/* 防线3：gcc -fstack-usage 生成 .su 文件，CI 校验最坏调用链深度 */
```

栈大小科学估算：① `-fstack-usage` 得每函数用量 → ② 画最坏调用链（含 ISR 嵌套×每层 32B 硬件帧）→ ③ ×1.5 安全系数 → ④ 运行期水位线验证。经验起点：简单裸机 1KB、RTOS 每任务 256~512B、printf 重度另加 512B。

## 6.5 map 文件阅读术（内存优化第一步）

```bash
arm-none-eabi-size firmware.elf        # text/data/bss 总览
arm-none-eabi-nm --size-sort -rn firmware.elf | head -20   # 最大符号 TOP20
grep -B2 '\.bss' firmware.map          # 三遍审读之一：找 bss 大户及其邻居
grep -A5 'Discarded' firmware.map      # 之二：看 gc-sections 裁掉了什么
grep 'LOADADDR' firmware.map           # 之三：验证 LMA 是否如预期
```

## 6.6 参数调试技巧

| 症状 | 测量手段 | 调什么 | 判据 |
|------|----------|--------|------|
| 全局变量初值全乱 | 反汇编 Reset_Handler | 确认拷贝循环存在 | _sidata 与 .data LMA 一致 |
| 变量运行中被改 | stack_paint 高水位 + MPU 保护区 | 抓越界现行 | 哨兵被冲掉的边界定位肇事者 |
| ramfunc 调用即 BusFault | map 查 .ramfunc 的 LMA/VMA | 启动代码补搬运循环 | 两地址分离且已拷贝 |
| gc 删了中断向量 | grep 向量表段名 | ld 中加 KEEP() | size 对比向量表长度 |

## 6.7 实测数据表：优化等级对同一工程的影响

| -O 等级 | text | 热点函数周期(点积1024) |
|---------|------|------------------------|
| O0 | 38.1K | ~41k cycles |
| Og | 31.6K | ~12k cycles |
| O2 | 30.9K | ~5.8k cycles |
| Os | 27.4K | ~6.1k cycles |
| O2+LTO | 28.3K | ~5.5k cycles |

规律：O0→Og 体积降最猛；O2→Os 再省约10%但热点略慢；LTO 大工程收益 5~15%。

## 6.8 排故速查表

| 现象 | 根因候选 | 定位路径 |
|------|----------|----------|
| DMA 数据永远收不到 | 缓冲在 CCM/TCM 等 DMA 盲区 | map 查变量地址落在哪个 MEMORY 区 |
| --gc-sections 误删段 | 自定义段无入口引用 | 一律配 KEEP；对照 Discarded 输出 |
| 链接顺序改变行为 | 段收集顺序=.o 链接顺序 | 固定 Makefile OBJ 顺序并注释原因 |
| 双弱符号冲突难查 | -fno-common 后双弱报错 | nm 查重定义；static 化收敛作用域 |

## 6.9 部署注意事项

1. 全静态项目 heap 设 0 并把 `_sbrk` 重载为死循环——让意外 malloc 在开发期立刻暴露
2. Noinit 段 `(NOLOAD)` 重启不清零，配合魔数判断冷热启动（[[ch29-低功耗设计]] Standby 场景刚需）
3. `--wrap=malloc` 把 malloc 重定向到 `__wrap_malloc`——给第三方库注入统计/失败注入的零侵入手段
4. Keil scatter file 与 GNU ld 的 MEMORY+SECTIONS 一一对应，跨工具链团队互为注释
5. 自定义参数区建议加 magic+CRC 双保险，缺失时回退默认值（Bootloader 参数区基础）

> [!example]- 🧪 动手实验 L6-1：用 -fstack-usage 绘制最坏调用链（35 分钟）
> 步骤：① CFLAGS 加 `-fstack-usage` 重编；② 汇总所有 .su 按栈耗排序取 TOP15；③ 从最大者出发人工追下层 .su 累加出最长链总深；④ 与 ld 栈大小对比算余量百分比。验收：产出「函数→累计字节」清单入库 docs/；余量 <50% 就扩栈或拆函数，ISR 嵌套另加每层 32B。

## 6.10 进阶话题

- 符号解析两阶段：symtab 合并（强/弱规则）+ 重定位回填 VMA——解释「调换 gcc 文件顺序会改变变量相对位置」
- gc-sections 工作流：`-ffunction-sections` 每函数独立 section → 从 ENTRY 出发可达性标记 → 未达丢弃——所以无入口引用的段必须 KEEP()
- 权威参考：GNU ld 手册 §3 仅 40 页值得通读；《Linkers and Loaders》(Levine) 第 5~6 章；libopencm3 的 linker scripts 目录是几十种芯片的极简模板库
- VTOR 重定位到 RAM 是 IAP 前置知识（见 [[ch30-Bootloader-IAP-OTA固件升级体系]]）

> [!warning]- ❓ FAQ
> **Q1：栈该给多大？**
> 科学方法四步（见 6.4），拒绝拍脑袋；水位线是唯一可信的最终裁决。
> **Q2：不用 malloc 还要留 heap 吗？**
> 设 0 并堵死 _sbrk——「意外的 malloc」开发期就炸比线上崩溃好一万倍。
