## 44.1 三层网关总体架构

把第四篇能力收束成工业级原型：**多南向采集 + MQTT 北向上云 + 本地规则引擎**，进程级隔离 + 统一数据总线。

| 层 | 成员与职责 |
|----|-----------|
| 南向采集层（独立进程×3） | modbus_master（RS485 ×32 从站轮询）、can_collector（SocketCAN 过滤订阅）、ble_scanner（BlueZ D-Bus 广播解析）——崩溃互不影响 |
| 核心服务层 gatewayd | 统一物模型归一化（JSON: point_id/value/ts/quality）→ 规则引擎（表达式求值/阈值联动/死区压缩上报）→ SQLite 时序缓存（断网队列+补传游标）→ MQTT 客户端（QoS1 + TLS 双向认证） |
| 北向与管理面 | 云端 IoT 平台（EMQX/ThingsBoard）、本地 Web 管理（LuCI 风，配置下发/日志导出）、OTA 服务（A/B 分区，RAUC/Mender 思想）、监控代理（心跳+资源水位外报） |

进程间通信：南向 ⇄ gatewayd 走 **Unix 域套接字（UDS）**；gatewayd ⇄ 云端走 **TLS/MQTT**。选「多进程+UDS」而非「单进程多线程」的核心理由：故障隔离（一个协议栈崩溃不拖垮全局）、可独立重启升级、语言异构（BLE 可用 Python 桥接）；代价是多一跳序列化开销。

## 44.2 南向适配器接口

```c
/* 南向适配器接口 —— 分层架构依赖倒置思想在 Linux 进程内的复用 */
typedef struct {
    int (*open)(dev_ctx_t *ctx);
    int (*poll_points)(dev_ctx_t *ctx, point_t *out, int max);
    int (*write_point)(dev_ctx_t *ctx, int pid, double val);
} proto_ops_t;
/* modbus 用 libmodbus；CAN 用 SocketCAN；
   BLE 用 gatt-dbus C API 或 python bluezero 桥接 */
```

统一物模型是防腐层：无论哪个协议进来，gatewayd 只认 `point_id/value/ts/quality` 四元组。新增 OPC UA 只需新写一份 ops 实现注册进来，核心层零改动——这就是扩展性验证的标准答案。

## 44.3 死区压缩上报：省流量神器

```c
/* 只有 |新值-上次上报值| > max(deadband, k*σ) 才发，
   且强制周期兜底（如 5min 一条心跳值），兼顾灵敏度与流量 */
bool should_report(double v, double last, double db) {
    return fabs(v - last) > db || (now() - last_ts > 300);
}
```

参数经验：deadband 按传感器噪声 σ 的 2~3 倍起步；周期兜底保证断点可追溯，防「静默漂移」长期不被发现。慢变模拟量配合死区压缩，上行流量常降一个量级（典型值）。

## 44.4 看门狗三级守护体系

| 级 | 机制 | 覆盖故障 |
|----|------|----------|
| L1 | systemd Restart=always 各服务自愈 | 单进程崩溃退出 |
| L2 | gatewayd 监控各南向进程心跳 socket，僵死 kill 重启 | 假死（不退但不干活） |
| L3 | 硬件 watchdog(/dev/watchdog) 由最核心进程喂 | 整机假死后强制复位 |

```c
int wd = open("/dev/watchdog", O_WRONLY);
write(wd, "1", 1);   /* 主循环每轮喂一次；timeout 由 dts/内核参数配置(如30s) */
```

原则：喂狗权只给最核心的 gatewayd，且以全部南向心跳健康为前提——否则半死状态会被无限续命。

## 44.5 SQLite WAL 与断网续传

- 断网期间点位入 SQLite 队列，恢复后按补传游标上行，云端按 point_id+ts 幂等去重；断网 24h 约 27 万点须在 10 分钟内补传完毕。
- **单写者纪律**：全系统只有 gatewayd 写库，其他进程经 UDS 查询——eMMC 上多进程直写必撞 SQLITE_BUSY。
- `WAL 模式 + synchronous=NORMAL` 是性能与安全的甜点位。

## 44.6 参数调试技巧

| 症状 | 测量手段 | 调什么 | 判据 |
|------|----------|--------|------|
| 轮询周期抖动大 | 打点统计轮询耗时分布 | 超时/重试参数、离线从站降频 | 32 从站 @1s 稳定闭环 |
| SQLITE_BUSY 偶发 | 查谁在持写锁 | 收敛 gatewayd 单写者；WAL+NORMAL | 72h 零 BUSY |
| MQTT 断链恢复慢 | 断网演练计时 | 重连退避与会话保持参数 | 断链自愈 <30s |
| watchdog 误复位 | 内核 log 复位原因 | 喂狗周期与 timeout 余量 ≥3 倍 | 复位风暴 50 次零误杀 |

## 44.8 排故速查表

| 现象 | 根因候选 | 定位路径 |
|------|----------|----------|
| Modbus CRC 错误集中在某从站 | 方向切换时序错 / 线缆 stub 过长 | 先换短直连验证；查其固件是否「发送返回即切方向」（ch28 同款问题） |
| SQLite 偶发 SQLITE_BUSY | 多进程同时写 | 收敛 gatewayd 单写者；WAL+synchronous=NORMAL |
| TLS 握手冷启动前 30s 必失败 | 系统时钟未同步致证书校验失败 | 把 SNTP 完成做成 MQTT 连接的前置条件事件，别并行碰运气 |
| 整机假死无法远程恢复 | WDT 未启用或喂狗进程选错 | 确认 /dev/watchdog 由 gatewayd 持有、timeout 配置合理 |

## 44.9 部署注意事项与 BOM

1. SNTP 同步完成是 MQTT(TLS) 连接的前置事件——证书校验对时钟极敏感；
2. OTA 接口按 RAUC/Mender 的 A/B 分区预留，签名校验不可省；
3. 监控代理外报心跳+资源水位，接 S3 台架做长期观测；
4. 硬件清单：ATK-DLRK3568(2GB+16GB，板载 CAN 座、485 外接收发器)；USB-RS485+Modbus Slave 软件模拟从站（先跑通再换真电表）；USB-CAN 适配器(candleLight 固件)；nRF52/ESP32 广播温湿度做 BLE 终端；云端 Docker 起 EMQX+InfluxDB+Grafana。

> [!example]- 🧪 动手实验 L44-1：断网续传与复位风暴演练（60 分钟）
> **步骤**：① 全链跑通后拔掉上行网络 24h（可用缩短版先验流程）；② 恢复网络观察补传；③ `kill -9` 全部服务进程；④ 脚本连续复位整机 50 次。
> **验收**：断网数据 10 分钟内补传完且云端无重复点；kill -9 后 systemd 全部拉起、数据零丢失；50 次复位 watchdog 兜底成功率 100%。

## 44.10 进阶话题与里程碑路线

- **git 分步路线**：M1 modbus 轮询引擎+离线降频 → M2 SocketCAN 过滤订阅 → M3 BlueZ D-Bus 扫描 → M4 gatewayd 核心（物模型+缓存+死区） → M5 云端链路(MQTT/TLS+Grafana) → M6 systemd+WDT 三级守护 → M7 文档与产测脚本，每步设验收门；
- **对照开源**：EdgeX Foundry / ThingsBoard IoT Gateway 学设备服务抽象与配置驱动架构（设备配置 schema 让新增点位改 JSON 不改代码）；OpenWrt+collectd 学插件化守护进程组织；EMQX 桥接规范学 Topic 设计与 QoS 最佳实践；RAUC 学 A/B 升级签名与原子切换；
- **规则引擎安全**：表达式求值文法要限制递归深度与执行时长，防恶意配置 DoS。

> [!warning]- ❓ FAQ
> **Q1：为什么不用单进程多线程省去 UDS 序列化？** 崩溃隔离、独立重启升级、异构语言三收益大于一跳拷贝开销；且 eMMC 单写者模型在多进程下更清晰。
> **Q2：断网补传会不会把云端打爆？** 按游标分批限速补传，云端幂等去重；27 万点的批量要预留带宽窗口。

> 1. 为什么选「多进程+UDS」而不是「单进程多线程」？给出至少三条工程理由与一条反面理由。
