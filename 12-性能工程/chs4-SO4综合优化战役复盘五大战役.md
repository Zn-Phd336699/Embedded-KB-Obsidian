## SO4.2 战役一：启动提速 4.5 s → 900 ms
**背景与测量**：GPIO 打点瀑布图([[ch56-启动流程深度剖析systemd提速]])——U-Boot 1.6 s+内核 2.1 s+init 0.8 s 三块都大；**最大单点是 initcalls 中一个 800 ms 的 PHY 就绪等待**。

| 假设 | 实验 | 结果 |
|------|------|------|
| H1 PHY 自协商固定等待可缩短 | 改轮询上限 | ✓ −600 ms |
| H2 网络驱动可延后 | 模块化后置加载 | ✓ −350 ms |
| H3 多个 initcall 可并行 | 内核不支持则模块化 | ✗ 收益小，放弃 |

## SO4.3 战役二：Linux 网关 CPU 78% → 31%（火焰图主战场）
```text
【证据链】perf 火焰图(ch16)三座大山：
  ssl_write 31%(AES 软算 19%) / json_parse 18%(cJSON 反复 malloc) / modbus_poll 忙等 12%
【假设】H1 AES 有硬件加速未启用 → 查 CONFIG_CRYPTO_DEV
       H2 JSON 库低效 → 换 yyjson 或改二进制协议；H3 轮询间隔过密 → 事件化改造
【实验】H1 ✓ 启用 crypto-dev+会话复用：ssl_write 31%→9%
       H2 ✓ yyjson+对象池：json_parse 18%→4%
       H3 △ 事件化 12%→5%，剩余为协议固有开销(接受)
【对比解读】前三塔并列=「系统性肥胖」多点治理；后仅剩 tcp 栈固有单塔=理论边界收官
【结论】CPU 78%→31%；附带收益：内存分配次数 −83%，jitter 同步改善
【金句】火焰图的价值不在第一张图，在第二张图——对比才产生结论
```

## SO4.4 战役三：RTOS 控制环 jitter 87 µs → 7 µs
**背景与测量**：DWT 打点直方图呈双峰——主峰 4 µs+次峰 80 µs(占 3%)；[[ch51a-可视化追踪Tracealyzer-SystemView]]回放锁定次峰时刻=Flash 参数写入任务的运行窗口。
**根因与对策**：H1 Flash 擦写阻塞总线致取指停顿(ch06)→ramfunc 化擦写函数+关 Cache 维护期补偿 ✓；H2 参数任务优先级过高抢占控制链路缓存/代码→降 prio 至控制环以下并分片写入 ✓。两措施叠加后次峰消失。
**结论**：P99 jitter 87 µs→7 µs；新增「参数写入影响实时性」检查项进设计 checklist。**双峰分布是周期性干扰的铁指纹——看到双峰先找周期源。**

## SO4.5 战役四：无线节点待机功耗 500 µA → 52 µA
**背景与测量**：Joulescope 电流瀑布([[ch29-低功耗设计]])分层——LED 指示 180 µA、I2C 上拉网络穿流 120 µA、传感器未休眠 95 µA、MCU 引脚振荡 60 µA、DC-DC 静态 45 µA，合计基线 500 µA。

| 假设 | 实验 | 单步电流 |
|------|------|----------|
| H1 LED 改低频闪烁 | 占空比降到 1/10 | ✓ −162 µA |
| H2 上拉改下拉驱动(电路约束允许) | 硬件微调 | ✓ −120 µA |
| H3 传感器支持休眠协议 | sensor sleep+PMOS 断电 | ✓ −93 µA |
| H4 存在浮空引脚(ch23) | 全引脚钉电平扫描 | ✓ −58 µA |

**结论与制度**：终值 **52 µA 超目标**；沉淀《低功耗设计 checklist》(原理图评审项 12 条)+《GPIO 钉电平自动扫描脚本》进产测([[chsd-S4-量产工程产测工装与老化]])。**功耗优化 70% 在硬件选型与电路，软件是最后 30% 的精修者。**

## SO4.6 战役五：OTA 升级成功率 91% → 99.8%
**背景与测量**：云端 5000 次样本失败分类——下载中断 46%、校验失败 22%、写入掉电 17%、切换失败 9%、其他 6%。**失败分布饼图直接指出主攻方向。**

| 失败类别 | 对策(假设) | 出处思想 |
|----------|------------|----------|
| 下载中断 46% | 分块+断点续传+指数退避重试 | [[ch63-网络编程与TLS从socket到安全上云]] |
| 校验失败 22% | 每块 CRC+整包 SHA 双层校验 | [[chfh-A8校验族谱CRC全家汉明HMAC边界]] |
| 写入掉电 17% | swap 日志幂等化 | [[ch30-Bootloader-IAP-OTA固件升级体系]] |
| 切换失败 9% | 自检项补齐+revert 兜底确认 | ch30 |

**实验矩阵与结果**：弱网模拟(丢包 5/10/20%)×断电注入(随机时刻)×200 台灰度三周收集 4200 次升级；91%→**99.8%**，剩余 0.2% 全部二次尝试自恢复，新增失败原因码上报使定位时间天级→分钟级。**可靠性提升的本质是把失败从黑盒变成分类清晰的遥测数据。**

## SO4.7 复盘报告标准结构（模板 v1/v2）
```markdown
《性能优化复盘：<标题>》—— v1 共七节，v2 增补至十节：
§1 背景与症状(量化基线)    §2 分析过程(工具+数据，含排除项)
§3 假设清单(H1..Hn 标注 ✓/✗/△) ← 失败假设记录是本文档的灵魂
§4 实施明细(commit 范围引用)   §5 结果对比(前后指标表+图表)
§6 经验沉淀(checklist 更新)    §7 遗留风险与后续计划
§8 能效维度(v2：J/mWh 口径、DVFS/睡眠策略联动)
§9 回归守护项(v2：CI 基线指标清单+阈值+脚本路径+责任人与复查周期)
§10 反模式自查(v2：本次是否触碰 SO4.8 清单？如何规避？)
```

## SO4.8 性能反模式库（十条「越改越糟」实录）
| # | 反模式 | 为什么糟 |
|---|--------|----------|
| 1 | 无基线就开始优化 | 无法证明收益也无法止损 |
| 2 | 只调参数不改结构 | 结构性瓶颈下参数收益趋零且反复震荡 |
| 3 | 测量代码改变被测行为 | 海森 Bug 制造机(ch16 教训) |
| 4 | 同时上多个优化再测总账 | 功劳无法归因，负优化被掩盖 |
| 5 | 用平均延迟汇报实时性能 | 掩盖 P99/max 尾部灾难([[ch45-实时性理论与调度算法]]) |
| 6 | 为省 RAM 关闭栈保护 | 省几百字节换来随机崩溃排查周 |
| 7 | 把 DMA 化当万能药 | 小数据量场景管理开销>收益([[ch26-DMA与Cache一致性]]) |
| 8 | 优化未证明的热点函数 | Amdahl 定律：非热点优化对整体无感 |
| 9 | 优化后不跑功能回归 | 性能换正确性是最亏的交易 |
| 10 | 一次性大规模重构式优化 | 不可回退不可评审不可归因——应拆成可验证的小步 |

## SO4.9 排故速查表（五战役经验映射）
| 现象 | 根因候选 | 定位路径 |
|------|----------|----------|
| 直方图出现双峰 | 周期性干扰源(如 Flash 写窗口) | Tracealyzer 回放对齐次峰时间戳→找周期任务 |
| 火焰图多塔并列无主导 | 系统性肥胖(多点低效叠加) | 逐塔治理后复测，直到剩单塔理论边界 |
| 待机电流远超预算 | 上拉穿流/浮空脚/外设未休眠 | Joulescope 分层瀑布→假设逐条独立验证 |
| OTA 失败率异常偏高 | 下载/校验/掉电/切换混杂 | 失败原因码分类统计→按占比排序主攻 |

## SO4.10 部署注意事项
1. **成果守护**：核心指标纳入 CI 基线告警(SO5 回归体系)——没有守护的优化会悄悄回退；
2. **知识扩散**：复盘文档强制团队内讲评一次——案例库是最快的团队成长燃料；
3. **收官与止损**：已达理论边界仍压榨=引入脆弱性；剩余问题修复成本>业务损失时停止，判据写进团队规范。

> [!example]- 🧪 动手实验 LN-SO4：四段式微复盘（30 分钟）
> **步骤**：选一个已知性能痛点 → 用现有工具量化基线 → 列 2~3 条假设并预估收益 → 逐条独立验证并记录每步数字。
> **验收**：产出一份含 ✓/✗/△ 标注的假设清单+前后指标对照表，且至少有一条失败或部分成功假设被诚实记录。

## SO4.11 进阶话题
- 双战役共同教训：最大突破都来自「把模糊问题拆成可分类的可测问题」(失败分类饼图/电流分段瀑布)——分解力就是性能工程的核心能力；
- 反模式 #4 的统计学根源：多变量同时改动无法归因，负优化被掩盖；Amdahl 定律则约束非热点优化的理论上限。

> [!warning]- ❓ FAQ
> **Q1：失败的假设为什么也要写进复盘？** 失败假设入档防止后人重走弯路——这是复盘区别于普通报告的灵魂(SO4.2 的 H3 即典型)。
> **Q2：什么时候宣布优化收官？** 剩余为固有开销(profiler 证明)、修复成本大于业务损失时——给出止损判据并写进规范。
