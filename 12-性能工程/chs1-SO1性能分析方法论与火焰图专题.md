# SO1 性能分析方法论与火焰图专题

> [!info] 导航
> ⏱ 40min | ★★★★☆ | 前置 [[chfk-A11机器人导航定位建图路径规划]] | → [[chs2-SO2-MCU系统优化实战]]
## 🎯 学习目标
- [ ] 能复述延迟/吞吐/CPU利用率/带宽/抖动的精确语义，并用分位数替代平均值下结论
- [ ] 会用「自顶向下五层分解 + USE 资源检查表」双框架完成归因，杜绝跳层猜测
- [ ] 能完成火焰图生成、判读与优化前后对比量化收益
- [ ] 能识别观测者效应与四大测量陷阱，产出可复现的测量报告
## SO1.1 性能分析五步法：没有方法论 = 随机改代码碰运气
```text
建立基线 → 测量 → 归因 → 优化 → 回归验证 （闭环回到基线归档）
① 基线先行：优化前采集并归档全部指标——没有对照就没有成果
② 批量测量：固定口径采 ≥1000 次，单次测量无意义
③ 分层归因：拿到数据才允许进入下一层，跳层猜测是头号浪费
④ 一次一变量：同时改三项，功劳无从归属、回退无从谈起
⑤ 同环境回归：温度/电压/编译选项/测试数据全部锁定并记录
```
## SO1.2 五大基础指标：先把词义钉死
| 指标 | 精确定义 | 高频误读辨析 |
|------|----------|--------------|
| 延迟 Latency | 单次操作从请求到完成的时间分布 | 「平均10ms所以快」是陷阱：P99=500ms 的系统会被平均值骗死，永远看分位数 |
| 吞吐 Throughput | 单位时间完成的操作数 | 吞吐高≠延迟低：攒批处理吞吐漂亮但单次延迟爆炸 |
| CPU 利用率 | 非空闲时间占比 | iowait 计入会误导；多核要按核分别看；利用率低≠不忙（可能在等锁） |
| 带宽 Bandwidth | 单位时间数据量 | DDR/总线带宽是嵌入式隐形天花板，选型期就要核算 |
| 抖动 Jitter | 延迟波动幅度(P99−P50) | 实时系统的第一指标——平均再好，抖一下就废 |
## SO1.3 双框架归因：自顶向下分解 + USE 检查表
```text
任何「系统慢」都按固定层次拆解，每层只回答一个问题：
L1 整机层：CPU 瓶颈还是等待瓶颈？  → CPU 占用/idle 分布
L2 进程层：哪个进程吃掉的？        → top 按 CPU 排序/pidstat
L3 线程层：进程内哪个线程？        → top -H/perf 按线程过滤
L4 函数层：线程内哪段代码？        → 火焰图/profiler
L5 行级层：哪一行、为什么？        → 反汇编/cache-miss 分析
MCU 版对应：整机电流→任务泳道(ch51a)→函数打点(DWT)→汇编热点
```
USE 法（Brendan Gregg）：对每种资源依次检查 Utilization(使用率)、Saturation(饱和度/排队)、Errors(错误计数)：

| 资源 | Utilization 查什么 | Saturation 查什么 | Errors 查什么 |
|------|--------------------|-------------------|---------------|
| CPU 每核 | mpstat/任务泳道占比 | runqueue 长度/抢占次数 | 软锁死/hardlockup |
| 内存 | free 各区水位 | kswapd 活动/缺页率 | OOM kill/ECC 错误 |
| 总线(DMA/SPI/I2C) | 事务占用率(LA 实测) | FIFO 满/仲裁等待 | NACK/CRC/BUS-OFF |
| 中断 | /proc/interrupts 增速 | 同 IRQ 排队/关中断时长 | spurious 计数 |
## SO1.4 延迟预算表：把「快」变成可分配的数字
「按键按下→屏幕响应」预算示例（总目标 100ms）：

| 环节 | 预算 | 实测 | 判定 |
|------|------|------|------|
| 按键扫描周期 | ≤20ms | 20ms | ✓ 贴线 |
| 事件队列传递 | ≤5ms | 2ms | ✓ |
| UI 任务唤醒+处理 | ≤30ms | 41ms | ✗ 超支点 |
| 渲染一帧 | ≤33ms | 29ms | ✓ |
| LCD 刷出 | ≤12ms | 11ms | ✓ |

结论一目了然：只有 UI 处理超支→只优化它→复测闭环。模糊的「快」变成可分配、可审计的工程指标。
## SO1.5 on-CPU vs off-CPU：火焰图最大的盲区
- on-CPU 分析统计「正在烧 CPU」的栈：Linux 链路 perf record -F 299 -g → stackcollapse-perf.pl → flamegraph.pl；
- off-CPU 分析统计「在等什么」（锁/IO/事件）：eBPF offcputime、ftrace 唤醒延迟、Tracealyzer 阻塞链(ch51a)；
- 判据：CPU 高→on-CPU 图；CPU 不高仍慢→立刻转 off-CPU 视角。MCU 侧由 Tracealyzer 导出或 DWT 采 PC 自制采样器转 folded 格式渲染。
## SO1.6 火焰图判读规则与六大误读
读图规则：X 轴=字母排序**不是时间**；**宽度=自身 CPU 时间占比（只有宽度才是成本）**；Y 轴=调用栈深度（顶=叶子），高度与耗时无关；找热点=找「宽而平顶」的塔；前后两图对比=找变矮的塔即量化收益。模式识别思想：形态高度模式化——宽而平顶=集中热点、细碎锯齿带=分散调用合计可观、深谷窄塔=递归或深层包装，看多了自然一眼定位。

六大典型误读：①把 X 轴当时间轴（时序请用 Tracealyzer/chrome tracing）；②认为塔越高越耗（只是栈深）；③以为颜色有语义（默认随机暖色仅区分相邻帧）；④采样少就否定工具（99Hz×60s≈6000 样本对 70% 级热点足够稳定）；⑤火焰图全平=没问题（它只见 on-CPU，等待型瓶颈要用 off-CPU 火焰图/ftrace 双视角）；⑥认为 MCU 上没法做（SysTick 采样 PC+离线符号化即可实现）。
## SO1.7 关键代码：MCU 穷人版采样火焰图
```c
/* SysTick 或独立低优先级定时器周期触发（200us~1ms 可调） */
void sampler_isr(void){
    uint32_t pc = get_stacked_pc();          /* 从 PSP 栈取被打断处的 PC */
    sample_buf[sample_idx++ & 4095] = pc;    /* 环形缓冲存原始地址 */
}
/* 主机侧：dump 样本数组 → addr2line 批量符号化
   → awk 折叠成 "root;task_sensor;sensor_read;spi_xfer 87" → flamegraph.pl */
```
三条注意：采样 ISR 本身约 30 周期，1kHz 时开销约 0.5%；只能采到正被抢占的任务，idle 与阻塞态是盲区(off-CPU 不可见)；-O2 内联让栈顶 PC 聚焦叶子函数，配合调用栈回溯更准但更复杂。
## SO1.8 时间测量方法学：打点之前先懂时钟
| 时钟源 | 精度/分辨率 | 适用测量 | 陷阱 |
|--------|-------------|----------|------|
| DWT CYCCNT(M3+) | CPU 周期级(6ns@168M) | 函数/代码段耗时 ★首选 | 变频时读数速率随之变化需换算 |
| RTC(32k LSE) | 约 30us 但绝对准 | 跨睡眠/天级统计 | LSE 温漂需校准 |
| clock_gettime(MONO) | ns 级接口 | 应用层打点 ★标准 | REALTIME 会跳变——测耗时必须 MONOTONIC |
| GPIO+逻辑分析仪 | 由 LA 采样率决定(us~ns) | 跨模块边界、ISR 链路 | 占引脚、通道数有限 |

打点规范四条：①成对测量——t0/t1 同一时钟源同一上下文；②统计口径——≥1000 次报 P50/P99/max；③预热排除——首跑含 cache 冷启动/I-Cache 填充，丢弃前 N 次；④侵入性声明——打点自身耗时要标注(通常 <0.5us)。观测者效应红线：测量代码总开销不得超过 5%，否则你在优化「测量带来的负载」而非真实问题。
## SO1.9 参数调试技巧
| 症状 | 测量手段 | 调什么 | 判据 |
|------|----------|--------|------|
| 平均正常但用户喊卡 | 分位数统计 P99/max | 排查长尾来源(重试/冷cache/攒批) | P99 回到预算额度内 |
| CPU 不高但系统仍慢 | off-CPU 火焰图/ftrace | 断阻塞链、异步化 | 等待时长下降可量化 |
| IPC 低于 0.4 | DWT CPICNT/CYCCNT | 开 flash 预取、改访存模式 | IPC 回升至 0.6 以上 |
## SO1.10 实测数据表
| 场景 | 指标A | 指标B |
|------|-------|-------|
| DSP 循环 IPC 实算 | CYCCNT=100000、CPICNT=72000 → IPC=0.72 流水线健康 | IPC<0.4 → 先开预取/查访存模式，不急着改算法 |
| race-to-idle 实测 | 48MHz 40mW×10s | 96MHz 25mW×5s+深睡 5s 能量省 37% |
| 利特尔法则例题 | λ=2000msg/s、W=400us → L=0.8 单消费者足够 | W=2ms → L=4 需 4 并行度或降 W |
## SO1.11 排故速查表
| 现象 | 根因候选 | 定位路径 |
|------|----------|----------|
| 报告称「很快」但体验卡顿 | 只看平均值掩盖长尾 | 强制报 P50/P99/max，对照延迟预算表 |
| 利用率高却找不到元凶 | 缺分层归因、跳层猜测 | 按 L1→L5 逐层下钻，拿数据再进下一层 |
| 优化后复测无变化 | 测量污染或环境漂移 | 校验打点开销 <5%，锁定环境重采基线 |
## SO1.12 部署注意事项
1. 基线先行：优化前先采集并归档「优化前基线」——没有对照就没有成果；
2. 一次一变量：同时改三项再测提升，你不知道功劳属于谁；
3. 测量侵入性校验：确认测量代码本身 <5% 开销；
4. 环境锁定：温度/电压/编译选项/测试数据全固定——不可复现的性能数字等于零；
5. 报告双受众：管理层看前后对比一句话，工程师附原始数据与复现命令。

> [!example]- 🧪 动手实验 LN-SO1：给 MCU 固件拍一张火焰图（35 分钟）
> **步骤**：挂 1kHz 采样定时器（SO1.7 骨架）→ 跑典型业务 60s → dump 4096 点环形缓冲 → addr2line 符号化 → 折叠 folded 格式 → flamegraph.pl 出图。
> **验收**：得到可交互 SVG；TOP3 热点合计占比 ≥50%；连续两次采样 TOP3 名次一致且占比偏差 <5 个百分点；采样 ISR 开销经 DWT 实测 ≤1%。
## SO1.13 进阶话题
- DWT 五计数器全家福：CYCCNT 总周期/CPICNT 理想周期(IPC=CPICNT÷CYCCNT)/EXCCNT 异常消耗/SLEEPCNT 睡眠周期/FOLDCNT·LSCNT 访存等待——A 核对应物 ARM PMU+perf stat；
- 能效权衡：race-to-idle 成立条件=高频平方级功耗<长时间低频底噪功耗；DVFS 三策略 powersave/schedutil(★默认)/performance 按预算表切换；EDP=E×D 综合惩罚能耗与延迟；
- 容量规划与 PGO：利特尔法则 L=λ×W 设计队列深度与 OTA 分块窗口，ρ→1 时排队延迟按 1/(1−ρ) 发散（资源留 30% 余量的数学依据）；PGO 因两阶段构建+剖面失配在嵌入式遇冷，务实替代=函数级 -O3 引导+链接脚本热路径布局+A 核 LLVM PGO 试点。

> [!warning]- ❓ FAQ
> **Q1：火焰图颜色深浅代表严重程度吗？** 默认随机暖色仅区分相邻帧无语义；可用红黄谱突出热点但需自行声明。
> **Q2：memcpy 占 25%，直接手写汇编优化它？** 不该。先归因——谁在上游频繁调它、能否少拷甚至零拷（结构改造），函数级优化永远是最后一步。
