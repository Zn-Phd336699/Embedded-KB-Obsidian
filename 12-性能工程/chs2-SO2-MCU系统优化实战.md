## 🎯 学习目标
- [ ] 能用启动瀑布图（GPIO 打点+逻辑分析仪）定位最大可压缩段并按收益排序动刀
- [ ] 能用 map 文件三遍审读法系统裁剪 Flash/RAM，产出《裁剪决策表》
- [ ] 会自测编译选项矩阵（-O0/-Og/-O2/-Os/-flto）并选定量产档位
- [ ] 能在「查表 vs 实时计算」「XIP vs 拷贝执行」间给出有数据支撑的取舍
## SO2.1 三大战场与启动瀑布图：先测后砍
MCU 性能战场只有三个：**启动要快、空间要省、CPU 要闲**。第一步永远是画启动瀑布图——各阶段入口翻转独立 GPIO，逻辑分析仪一次抓全链（µs 级精度零侵入；Linux 侧对应 systemd-analyze）。条形长度即优先级：最长的条最先动刀，没有这张图的一切优化都是盲调。
## SO2.2 启动全链优化清单（按收益排序）
| # | 措施 | 典型收益 | 风险/代价 |
|---|------|----------|-----------|
| 1 | 关 U-Boot 倒计时与冗余命令(CONFIG_BOOTDELAY=0) | −0.5~1.5s | 失去快速进 CLI 能力(留按键中断后门) |
| 2 | 非关键驱动改模块延后加载 | −0.3~2s | 使用时序必须晚于加载完成(审计调用点) |
| 3 | 外设自检从全量顺序改并行+超时 | −100~800ms | 自检覆盖率不得降低(S4 门禁) |
| 4 | Sensor 预热与业务初始化重叠执行 | −50~200ms | 注意电源峰值叠加(浪涌) |
| 5 | 启动期日志降级为 ERROR + Flash 读加速(QSPI 提速/预取) | −30~150ms | QSPI 提速稳定性需高低温复验 |
## SO2.3 启动的理论下限：哪些时间砍不动
| 不可压缩段 | 构成 | 下限估算方法 |
|------------|------|--------------|
| BootROM+复位电路稳定 | 芯片固化行为+RC 时序 | 规格书 tPOR 参数，典型 10~50ms |
| DDR 训练/初始化 | ZQ 校准+读写训练扫描 | 示波器抓 DDR_CLK 到稳定；LPDDR4 典型 80~200ms |
| 内核解压+早期初始化 | 与镜像大小/主频相关 | 理论=镜像字节/总线带宽×系数；实测为准 |
| 存储介质就绪 | eMMC 初始化/NAND 读取 | JEDEC 初始化时序固定部分不可省 |

结论框架：**可优化空间 = 实测总时长 − Σ不可压缩段**。先算理论地板再评估投入产出——「再快也不可能 100ms」的判断由此而来。
## SO2.4 XIP vs 拷贝执行决策表
| 维度 | XIP(QSPI 内存映射) | 整包拷贝到 RAM 执行 |
|------|--------------------|---------------------|
| 启动速度 | 快(免搬运) | 慢(需先搬) |
| 运行性能 | 受 QSPI 随机读延迟影响(cache miss 代价高) | **零等待最优** |
| RAM 占用 | 几乎为零 | =代码段全量 |
| 擦写自身 | 同 bank 冲突→ramfunc 兜底 | 天然安全(RAM 中运行) |

决策口诀：**启动快选 XIP、跑得快选拷贝；两者兼得=双 bank 或 XIP 预取后搬移**。QSPI 预取对两条路线都是无损第一步。
## SO2.5 编译选项全组合实测矩阵（同一 F407 工程口径）
| 配置 | Flash(KB) | 热点周期(点积1k) | 建议档位 |
|------|-----------|------------------|----------|
| -O0 | 386 | 41200cy | 仅调试 |
| -Og | 322 | 12100cy | 日常开发 ★ |
| -O2 | 315 | 5900cy | 量产默认 |
| -Os | 279 | 6200cy | Flash 紧张 |
| -O2+LTO(-flto) | 288 | 5400cy | 跨模块内联(-O3:334KB/5500cy 收益有限；+PGO 试点 285KB/5200cy) |

读表纪律：数值随代码特征波动，**每个项目必须自测一份本表**，趋势才是可迁移的结论。
## SO2.6 CPU 负载下降手段库（含查表取舍框架）
| 手段 | 适用场景 | 实测收益(F407 口径) | 注意事项 |
|------|----------|---------------------|----------|
| 轮询改中断/DMA 卸载 | UART/SPI 轮询收发 | CPU 占用 −60~95% | 复杂度上升；DMA 一致性(ch26) |
| 查表替代计算(sin/cos/CRC) | M0 无 FPU 或热点函数 | 该函数 ×3~10 提速 | +Flash；精度档位选择 |
| 定点替换浮点 / DSP 库·SIMD | 无 FPU 型号/并行热点 | ×2~5 / ×1.5~3 | M4F 上定点理由变为「确定性」；仅限 profiler 热点 |
| 降低采样/上报频率 ★最被忽视 | 业务允许时 | 线性正比 | 需求侧确认而非技术侧拍板 |
| 合并小事务批量读写 | 多寄存器 I2C/SPI | 总线事务数 −70% | 协议层配合(批量帧) |
| 编译矩阵重选(-Os/LTO) | 全局 | 体积 −15% 或速度 +10% | 回归全覆盖后切换 |

查表取舍三问：①调用频度多高（低频不值得换）？②Flash 余量允许多大表（大小=档位数×字宽）？③精度能否接受档位化（连续需求→实时计算+插值）？
## SO2.7 关键代码：map 文件三遍审读法
```bash
arm-none-eabi-nm --size-sort -r -S fw.elf | head -20   #第一遍【找大户】TOP20：
#   典型发现： printf 全功能版 28KB / 调试表格 6KB / 未用 HAL 外设驱动
grep -c " .text.*debug\|test_" fw.map                  #第二遍【找漏网】该删没删：
#   测试代码是否被宏隔离？
grep -A2 "\.bss" fw.map | sort -k2 -rn | head          #第三遍【找错位】RAM 大户四问：
#   这个缓冲能减半吗？ 能多通道共享吗？ 能挪 CCM 吗？ 能峰值复用吗？
#输出物：《裁剪决策表》每行=符号/现状/动作/预计节省/负责人——裁剪变成项目管理。
```
## SO2.8 RAM 多区分配决策矩阵（CCM/主 SRAM/SDRAM）
| 数据类型 | CCM(CPU独占) | 主SRAM(DMA可达) | 外部SDRAM |
|----------|--------------|-----------------|-----------|
| 任务栈/热函数(ramfunc)、PID/滤波等高频小数据 | ★首选 | 可用 | - |
| DMA 缓冲(UART/SPI/ADC) | ❌ 禁止(不可达, ch06) | ★唯一选择(32B 对齐) | 视控制器 |
| 大容量日志/帧缓冲、NoInit 区 | ❌ 容量不足 | 紧张时外移 | ★首选(NoInit 掉电丢失✗) |

DMA 卸载 CPU 的前提是把缓冲放对地方：主 SRAM 且 32 字节对齐，否则轻则打折重则总线错误。
## SO2.9 向量表 RAM 重定位：中断延迟的直接收益
```c
/* 操作： 把向量表拷入 RAM 并 VTOR 指向它(ch24 进阶) */
memcpy((void*)0x20000000, FLASH_VT, VT_SIZE);   /* 或由 ld 分配 .ramvtab 段 */
SCB->VTOR = 0x20000000;
/* 实测口径(168MHz, LA 统计 10 万次 EXTI)：
   Flash 向量表中断进入平均 0.45us → RAM 向量表 0.38us (省约 15%)
附带红利： 运行期可动态换表(IAP/ch30)；代价： 占用 512B~2KB RAM。
建议： 启动敏感+中断密集产品采用；普通业务收益有限。 */
```

## SO2.11 参数调试技巧
| 症状 | 测量手段 | 调什么 | 判据 |
|------|----------|--------|------|
| 启动时间周周不同 | GPIO 瀑布图逐段 diff | 锁 bootdelay/驱动顺序/日志级别 | 各段时长复现 ±10% 内 |
| Flash 用量逼近上限 | nm size-sort TOP20 | 精简 printf/清死代码/LTO | 用量回落 <85% |
| QSPI XIP 跑分不达标 | cache miss 统计 | 开预取或改拷贝执行 | 热循环接近 RAM 执行水平 |
## SO2.12 排故速查表
| 现象 | 根因候选 | 定位路径 |
|------|----------|----------|
| Flash 突增几十 KB | 新依赖整库链接/调试代码未宏隔离 | nm TOP20 + 第二遍 grep test_ |
| 启动比基线慢数百 ms | bootdelay 回来/驱动顺序变化 | 重抓瀑布图与基线逐段对比 |
| DMA 缓冲数据错乱 | 缓冲放 CCM 或未对齐 | 对照 SO2.8 矩阵查段地址与对齐 |
| -O2 后行为异常 | 未定义行为被暴露(volatile 缺失) | -Og 复现对比+反汇编核查(ch05) |
## SO2.13 部署注意事项
1. 可维护性红线：热点手写汇编必须配等价 C 参考实现+注释互指——没人读得懂的优化是负资产；
2. 回归门禁同步升级：结构级优化（池化/合并）必须先补单元测试再合入；
3. 极限余量管理：Flash 用到 >90% 即触发架构评审——下次需求的生存空间比本次优化更重要；
4. 功耗联动复核：提频/加 DMA 可能推高待机功耗（[[ch29-低功耗设计]] 联动）；
5. 反模式文档化：记录「试过但不划算」的手段及原因——防止团队三个月后再踩一遍。
> [!example]- 🧪 动手实验 LN-SO2：map 审读+启动摸底（35 分钟）
> **步骤**：对自己工程跑三遍审读（SO2.7）→ 列《裁剪决策表》≥3 行 → 抓一次 GPIO 启动瀑布图 → 按 SO2.3 公式算理论地板。
> **验收**：决策表每行有预计节省数字且合计 ≥10KB 或 ≥3% Flash；瀑布图各段时长导出成表；写出「可压缩空间=实测总时长−Σ不可压缩段」的准确数值。
## SO2.14 进阶话题
- 中断负载治理三步：NVIC//proc/interrupts 计数排名→单 IRQ 高频三嫌疑归因（电平未清源风暴/阈值太灵敏/本该 DMA 化的逐字节中断）→组合拳（硬件消抖+FIFO 阈值中断+NAPI 式关中断轮询混合）；红线：任一单一 IRQ ≤整机 CPU 的 10%；
- 启动天花板意识：DDR 训练与 JEDEC 初始化是硬地板，「可优化空间」公式先行评估投入产出；
- 开源参照：Zephyr 性能调优文档；grbl 源码的极致资源利用范本。
> [!warning]- ❓ FAQ
> **Q1：为什么量产不直接上 -O3？** 本例 -O3 热点 5500cy 对 -O2 的 5900cy 仅快 7%，体积反涨至 334KB；只对 profiler 证明的热点函数做函数级 -O3。
> **Q2：启动能做到 100ms 以内吗？** 先加总不可压缩段（tPOR+DDR 训练+介质就绪），地板超 100ms 则无讨论意义——用 SO2.3 公式回答而不是拍脑袋。
