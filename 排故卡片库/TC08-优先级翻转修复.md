# TC08 优先级翻转修复

## 现象
高优先级任务偶发性长时间阻塞甚至错过 deadline，但 CPU 占用率并不满载；触发条件：低优先级任务持锁期间，无锁的中优先级任务持续抢占运行。

## 环境与适用范围
FreeRTOS/RT-Thread/Zephyr 等抢占式 RTOS（Mars Pathfinder 经典案例）。协作式调度、时间片轮转独占系统不适用。

## 取证过程
1. Tracealyzer/SystemView 导出任务时间线：找 H 任务 Ready→Running 的超长间隔。
2. 检查该间隔内 CPU 在跑谁：若是无锁的中优先级任务 M，翻转成立。
3. 审查 H 等待的锁的创建 API：`xSemaphoreCreateBinary` 还是 `xSemaphoreCreateMutex`。
4. 统计持锁最长执行路径，评估临界区是否过肥。

## 根因
二值信号量不带优先级继承：L 持锁后被 M 抢占，H 因等锁只能旁观，实际等待时长被 M 的运行时间支配——优先级语义被「倒转」。互斥量的优先级继承协议会在 H 阻塞于锁上时临时把 L 抬到 H 的优先级，迫使 L 尽快跑完临界区释放锁。

## 修复方案
```c
/* 反例：二值信号量当锁用 —— 无优先级继承，翻转温床 */
SemaphoreHandle_t bad_lock = xSemaphoreCreateBinary();

/* 正解：互斥量自带优先级继承（configUSE_MUTEXES=1）*/
SemaphoreHandle_t g_mux = xSemaphoreCreateMutex();

void low_prio_task(void *p)               /* 低优先级 L */
{
    if (xSemaphoreTake(g_mux, pdMS_TO_TICKS(5)) == pdTRUE) {
        update_shared_table();            /* 临界区务必短小精悍 */
        xSemaphoreGive(g_mux);
    }                                     /* L 在此期间不会被 M 抢走太久 */
}
```

## 预防措施
- 共享资源一律用 Mutex；二值信号量只用于事件同步
- 临界区内禁止调用任何可能阻塞的 API（队列/延时/打印）
- 定期用 Tracealyzer 审查最长阻塞链与 deadline 余量
- 中断服务程序不得使用互斥量（ISR 无继承语义）
- 更严格场景考虑优先级天花板协议（RT-Thread/Zephyr 支持）
