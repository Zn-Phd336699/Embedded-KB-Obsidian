# TC30 观测体系 L0/L1/L2 升降级

## 现象
故障复盘发现日志翻 30 分钟定位不了问题（观测不足）；或 Prometheus+Loki+Jaeger 全家桶上线后维护成本压垮迭代、仪表没人看（过度建设）。缺的是分层投入判据。

## 环境与适用范围
适用嵌入式/Linux 产品线的可观测性规划（日志/指标/追踪三层）。1~10 人小团队最易在两个极端间摇摆。

## 取证过程
1. 拉近 3 个月故障复盘：MTTR 与当时可用的观测手段逐一对照。
2. 统计仪表查看频次与告警 actionable（可据此行动）比例，识别僵尸建设。
3. 按下方触发条件逐服务判定升降级，各写一页 ROI 说明。
4. 单服务试点验证收益后再推广，避免一刀切。

## 根因
三层观测成本与收益差一个数量级：L0 日志事后追溯、L1 指标分钟级发现问题、L2 追踪跨服务延迟归因。没有「何时升级/降级」的客观判据，就会凭直觉要么欠配要么过配。

## 修复方案
升降级触发条件：

| 层级 | 接入改造 | 存储运维成本 | 升级触发 / 降级触发 |
|------|----------|--------------|----------------------|
| L0 日志 | 低：日志库+字段规范 | 低：滚动文件 | 地基，常驻 / 字段无规范则先治理 |
| L1 指标 | 中：埋点+采集端 | 中：TSDB+值守 | 同类故障二次发生且查日志超 30min / 告警从不 actionable 则合并 |
| L2 追踪 | 中高：SDK+上下文透传 | 中高：采样控成本 | 调用链 ≥3 跳或 p99 劣化不知哪段慢 / 采样降至 1%（错误全采） |

```yaml
  # OTel Collector 尾部采样：错误全采 + 基线 1%，控住 L2 成本
processors:
  tail_sampling:
    decision_wait: 10s
    policies:
      - name: errors
        type: status_code
        status_code: {status_codes: [ERROR]}
      - name: baseline
        type: probabilistic
        probabilistic: {sampling_percentage: 1}
```

## 预防措施
- 每引入一层观测先写一页 ROI 预算书（成本对比预期 MTTR 收益）
- 告警必须 actionable 且含处置指引，否则不准上线
- 季度观测审计：删除零查看仪表与静默告警规则
- L0 阶段就预埋 trace_id 字段，未来升级 L2 无缝衔接
- 观测配置纳入代码评审与版本管理
