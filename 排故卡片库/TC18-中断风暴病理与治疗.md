# TC18 中断风暴病理与治疗

## 现象
top 中 %irq 或某 kworker 占用异常，`/proc/interrupts` 某中断计数疯涨，系统卡顿；示波器见中断引脚持续有效电平或密集脉冲。典型触发：外设申请了中断但标志未被清除。

## 环境与适用范围
适用 Linux request_irq（默认电平触发共享线）与 MCU 的 EXTI/NVIC 同构问题。边沿触发 + 机械抖动也会形成伪风暴；纯轮询外设不涉及。

## 取证过程
1. `cat /proc/interrupts` 间隔 1s 两次求差，锁定失控中断号与设备。
2. `mpstat -P ALL 1` 区分硬中断（%irq）与软中断（%soft）占比，判断风暴发生在上半部还是下半部。
3. 示波器/逻辑分析仪抓中断线：持续电平 → 电平触发未清标志；密集窄脉冲 → 抖动或外设反复申请。
4. `perf record -e 'irq:irq_handler_entry*' -a sleep 5` 或 ftrace events/irq/enable 统计进入频率。
5. 对照芯片手册核对状态寄存器清法（多数为 W1C 写 1 清零）与清除顺序。
6. 内核侧佐证：日志出现 irq N: nobody cared 并最终 Disabling IRQ，即无人认领型风暴。

## 根因
电平触发的语义是「线保持有效就再次进入」。ISR 未清外设标志（或先解屏蔽后清标志），退出瞬间条件仍成立 → 立即重进 → 风暴；共享线上 handler 误返 IRQ_NONE 还会被判无人认领而禁用。

## 修复方案
```c
static irqreturn_t adc_isr(int irq, void *dev)
{
    struct adc *a = dev;
    u32 st = readl(a->base + ADC_STS);

    if (!(st & ADC_STS_EOC))                 /* 共享线：不是我的中断 */
        return IRQ_NONE;
    writel(ADC_STS_EOC, a->base + ADC_STS);  /* 先清标志(W1C)，再做其余事 */
    complete(&a->done);
    return IRQ_HANDLED;
}
/* 耗时处理下沉内核线程，风暴时可被调度限流 */
devm_request_threaded_irq(dev, irq, adc_isr, adc_thread_fn,
                          IRQF_SHARED | IRQF_ONESHOT, "adc", a);
```

## 预防措施
- 电平型 ISR 第一行清标志，「先清后做」写入评审 checklist
- 共享中断必须正确返回 IRQ_HANDLED / IRQ_NONE
- 新驱动 bring-up 先用示波器看中断线行为再接软件
- 驱动内加风暴熔断：单位时间计数超阈则 disable 中断源并上报
- 机械开关类输入一律边沿触发 + 消抖
